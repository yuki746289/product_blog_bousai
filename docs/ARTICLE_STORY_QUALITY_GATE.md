# 防災ブログ 記事ストーリー品質ゲート

作成日時: 2026-09-08 JST  
更新日時: 2026-09-09 17:00 JST  
位置づけ: public側作業コピー  
正本: `yuki746289/product_blog_rules` の `sites/bousai/rules/ARTICLE_STORY_QUALITY_GATE.md`

## 必須6項目

### 1. タイトル整合性
タイトルで約束した内容が、冒頭から自然な順序で説明されているか。

### 2. 記事の地図（概要）
「この記事では何を、どの順番で説明するか」が初見で分かるか。

導入では原則、次を示す。
1. 読者の問題・迷い
2. 先に知るべき結論・最初の行動
3. この後の説明順
4. 安全上の中止条件が重要な記事では、安全確保へ切り替える判断

#### 冒頭概要の最低品質
概要は短さを優先しない。初見読者が冒頭だけ読んでも、**「なぜ読むのか」「まず何をするか」「この後何が分かるか」**を理解できることを優先する。

- 記事テーマを言い換えただけの1〜2文で終わらない
- 読者の困りごと・危険・判断ポイントのいずれかを具体化する
- 「確認します」「解説します」だけでなく、先に取る行動または判断基準を示す
- 主要H2が多い記事では、主要論点または時間軸を2〜5項目程度に要約する
- 安全記事では必要に応じて作業の中止条件・避難への切替条件にも触れる
- 導入・結論の200〜400字程度は説明不足を見つける警告目安であり、文字数ノルマにはしない。必要な説明があれば超えてよい

#### 本文要約としての概要（必須）
概要はタイトルから連想して別途作文せず、**本文を完成させた後に本文を圧縮して作る**。

1. タイトルで約束した対象・範囲を本文で回収する
2. 本文の主要H2を2〜5個程度の意味のまとまりへ圧縮する
3. その圧縮結果を概要として書く
4. `タイトル ↔ 本文 ↔ 概要` の三者を照合する

記事を固有のものにしている情報を必要な範囲で残す。

- 地域記事: 地域名、対象災害・出来事、現在の備えへつなぐ材料
- 比較記事: 比較対象、主要な比較軸、比較の目的
- 商品記事: 対象用品、用途・選び方、主要な注意点
- 対象者別記事: 誰向けか、その対象者特有の困りごと・備え
- 災害史記事: 地域・災害名/年代等の主要事例、そこから現在何を考える記事か

タイトル語を機械的に全部復唱することが目的ではない。ただし、記事固有の要素が概要から抜け、**同カテゴリの別記事へそのまま流用できる文章なら `FIX`** とする。

例:

タイトル: `鹿児島市・桜島の噴火史｜大正噴火と降灰データから考える火山灰対策`

不足:
> 日常的な降灰への対応と大規模噴火への備えを分けて整理します。

適切な方向:
> 鹿児島市・桜島について、1914年の大正噴火、近年の降灰データ、降灰量階級、大規模噴火想定をつなぎ、日常の降灰対策と大規模噴火への家庭の備えを整理します。

#### 公開同期の確認（必須）
Markdownを編集正本とする記事では、**公開ページの概要もMarkdown導入から生成・同期する**。

- Markdown導入とpreviewの `article-lead` が一致する
- production/publicの `article-lead` が最新Markdown導入を反映する
- 本文更新後に概要だけ旧文のまま残さない

Markdown側がPASSでも、公開概要が古ければ `FIX` とする。

テーマの言い換えだけで終わり、読者が最初に何をすればよいか分からない概要は `FIX` とする。

### 3. 説明の接続
H2/H3が突然始まらず、「なぜ次にこれを説明するのか」が分かるか。

### 4. 箇条書き品質
単語を並べただけになっていないか。必要なら「用途・理由・注意点」を説明する。

### 5. 視覚理解
種類の違い、配置、手順など、文章だけより画像・図表が明らかに分かりやすい箇所を見逃していないか。

### 6. リンクの文脈性
関連記事・商品記事を「最後にまとめて」だけでなく、読者が必要になる説明箇所にも配置する。

## 判定ルール

各記事で次を記録する。

| 項目 | 判定 |
|---|---|
| title_alignment | PASS / FIX |
| article_map | PASS / FIX |
| section_connection | PASS / FIX |
| list_quality | PASS / FIX / N/A |
| visual_understanding | PASS / ADD / N/A |
| contextual_links | PASS / FIX / N/A |
| fix_location | H2/H3名・該当段落・該当文 |
| fix_reason | 読者がどこで迷うかを具体的に記録 |

上記6項目のうち1つでも `FIX` があれば最終品質を `PASS` にしない。

`visual_understanding: ADD` は、画像がないと理解不足になる場合は `FIX` と同等に扱う。補助的価値のみなら本文をPASSとし、画像追加タスクとして管理できる。

過去にPASS済みの記事も、新基準ではPASSを引き継がず再判定する。

## 判定の具体化

### タイトル整合性
- タイトルに含まれる主要な約束を本文で回収する
- 主要な答えを長く探させない
- 「まとめ」の後にタイトル回収に必要な重要章を残さない

### 記事の地図
導入では、読者の問題、先にすること、本文の説明順が一致しているか確認する。時間軸や段階が重要な記事は、その順番を冒頭でも示す。

### 説明の接続
- 前章から次章へ論理・時間・判断のつながりを持たせる
- 同じ論点を離れた複数章へ分散しない
- 「まとめ」「チェックリスト」は原則として主要説明の後に置く

### 箇条書き品質
箇条書きは情報圧縮に使い、説明省略には使わない。
必要に応じて「何に使う」「なぜ必要」「いつ使う」「注意点」を示す。

### 視覚理解
次は画像・図表を積極的に検討する。
- A/Bの種類・構造の違い
- 配置・位置関係
- 3段階以上の手順
- 避難経路・水の流れ・高低差
- 画面や地図の「どこを見るか」

例: 携帯トイレと簡易トイレは「既存便器を使うか、便座自体を用意するか」を図で比較する。

### リンクの文脈性
- 詳細を知りたくなる直後に関連記事を置く
- 商品が必要になる文脈で商品記事へ接続する
- 記事末一覧は補助導線とし、唯一の導線にしない
- リンク先を読まないと本文が成立しない書き方は避ける

このゲートは文字数・情報量・事実確認とは別軸で運用する。情報が多くても、読者の理解順が崩れていればPASSにしない。
