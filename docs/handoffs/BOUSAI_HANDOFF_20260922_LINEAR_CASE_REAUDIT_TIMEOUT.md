調査方法:

1. 地方気象台・測候所等の「気象速報」「過去の災害」「気象災害史」を年単位で確認し候補母集団を作る
2. 気象庁の線状降水帯統一事例一覧・年度別実績で実発生を照合
3. 地方気象台の個別速報・気象庁「災害をもたらした気象事例」を確認
4. 自治体・国交省・消防庁等の一次資料で被害情報を補完
5. 観測記録で雨量・観測史上順位を確認
6. 検索エンジンは一次資料発見の補助に限定
7. 候補ごとに期間・現象・地域根拠・一次資料・分類・採否理由を残す

調査終了条件:

- 直近/過去それぞれ最大10件の適格候補を確認した、または
- 対象期間の公式アーカイブ・主要一次資料を年単位で一巡した

**5件見つかっただけでは調査終了にしない。**

分類:

- A = 線状降水帯実発生
- B = 関連する重大豪雨・局地的大雨
- C = 予測・可能性の呼びかけのみ
- H = 歴史的豪雨

現行制度以前の豪雨を雨域形状・雨量・被害だけで遡及的に線状降水帯認定しない。

## 6. タイムアウト対策

今回のタイムアウト原因は、1回の処理で多数記事・大きな本文を取得し、複数更新をまとめて実施したこと。

今後は以下を厳守する。

### A. 1ターンの作業単位を小さくする
- 原則1記事
- 最大でも「本文 + review + registry + test」の1セット
- 5記事まとめ取得は禁止

### B. GitHub取得を小さくする
- 全文が不要なら `fetch_file` の行範囲を使う
- 必要な見出し周辺だけ取得
- 巨大JSON出力を避ける
- 同じファイルを何度も全件取得しない

### C. 進捗をGitへ逐次保存
この引継ぎMDを作業のチェックポイントとして使用する。

大きな節目ごとに追記:
- B073完了
- B074完了
- ...
- CI修正完了
- デプロイ前報告完了

会話が切れても、このファイルだけ読めば再開できる状態を維持する。

### D. 小さいコミット
例:
- `Reaudit B073 Kyushu regional cases`
- `Sync B073 review and registry`
- `Reaudit B074 Kanto Koshin cases`

一度に大量コミットを作らない。

### E. CIは節目で確認
記事1件ごとにGitHub Actionsを何度も手動実行しない。
通常のpushで走るCIを利用し、Actions枠を節約する。

### F. 会話再開時
次スレッドでは最初にこのファイルを読む。
過去会話全文の再取得や14都県の再調査は不要。
