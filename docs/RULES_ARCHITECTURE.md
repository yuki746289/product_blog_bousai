# ルール体系・正本アーキテクチャ

更新日: 2026-09-23

## 1. 目的

複数サイトで共通利用するルールと、サイト固有ルール、専門ポリシー、実行チェック、レビュー記録を分離し、**同じ基準を複数ファイルで独立管理しない**。

品質基準は削らず、適用対象を明示して必要なモジュールだけを読む方式とする。

## 2. 5層構造

| 層 | 役割 | 正本例 |
|---|---|---|
| L1 共通原則 | 全サイトで再利用する品質・専門家・SEO・画像・制作原則 | `common/` |
| L2 サイト設定 | 共通原則の REQUIRED / CONDITIONAL / N/A、サイト目的・優先順位 | `sites/<site>/rules/*PROFILE.md`, `*SITE_SPEC.md` |
| L3 専門ポリシー | サイト内の特定テーマ・記事型だけに適用する詳細ルール | 災害事例、地域災害史、Amazon、SERP等 |
| L4 実行ゲート | 作成・レビュー・公開時にPASS/FAILを判定するチェックリスト | ARTICLE / SITE_RELEASE / preflight |
| L5 記録・証跡 | 実施したレビュー、監査、調査、進捗。規範そのものではない | reviews / research / audit / backlog |

継承順は **L1 → L2 → L3 → L4** とする。L5は判定結果・証跡であり、L1〜L4を上書きしない。

## 3. 優先順位

具体的なサイト・記事型ルールを優先する。ただし次の上位制約は下位都合で弱めない。

1. 人命・安全・重大損害の回避
2. 法令・権利・プライバシー
3. 正確性・根拠・情報鮮度
4. アクセシビリティ
5. 読者理解・UX
6. 情報設計・技術的信頼性
7. SEO・ブランド・配信
8. 収益・CV

## 4. チェックIDの名前空間

同じ `C01` を別意味で使わないため、今後は次を正本表記とする。

| 名前空間 | 用途 |
|---|---|
| `GCxx` | 全サイト共通チェック (`common/COMMON_SITE_CHECKLIST.md`) |
| `Cxx-yy` | 防災ブログの記事レビュー (`ARTICLE_REVIEW_CHECKLIST.md`) |
| `Sxx-yy` | 防災ブログのサイト横断チェック (`BOUSAI_SITE_REVIEW_CHECKLIST.md`) |
| 専用ID | Amazon等、個別preflightで必要な場合 |

既存の記事別記録にある `Cxx-yy` は互換性のため変更しない。

## 5. 正本とコピー

- `common/` の共通ルールをサイト配下へ複製して別正本にしない。
- `sites/bousai/rules/` は防災固有ルールの正本。
- `product_blog_bousai/docs/` は制作・テストで使う**作業コピー**であり正本ではない。
- 互換パスを残す必要がある場合は、内容を複製せず「正本への案内」だけを置く。
- ルール変更はprivate正本を先に、または同一作業単位で更新し、必要なpublic作業コピーを同期する。

## 6. モジュール適用

全チェックを全ページへ機械的に適用しない。

### 常時
- 共通GCのうちサイトプロファイルでREQUIREDなもの
- 防災記事の基本品質・安全・同期・UX・アクセシビリティ

### 条件付き
- 実在災害事例を主要要素として扱う → `DISASTER_CASE_RESEARCH_POLICY.md`
- 地域災害史 → 上記 + `LOCAL_DISASTER_HISTORY_POLICY.md`
- 線状降水帯県別 → 災害事例 + 地域 + 線状降水帯固有条件
- 商品/Amazon → affiliate / Amazon preflight
- Q&A → Q&A項目
- 数値集計・ランキング・可視化 → データ/統計レビュー
- 共通CSS/JS/ナビ/ビルド → サイトリリースチェック

## 7. 重複防止

同じルールを詳細に記載する正本は原則1ファイルにする。

他ファイルでは次のいずれかに限定する。

- 1〜3行の要約
- 適用条件
- 正本への参照
- その記事型だけの追加条件

件数・閾値・定義のように将来変わり得る値を複数正本へ重複記載しない。

## 8. ルール追加時

新しい問題が発生したときは次の順で判断する。

1. 既存ルールで検知できるか
2. 既存項目の具体例追加で足りるか
3. 同じ問題が複数ページで起こるか
4. 全サイト共通か、防災共通か、特定記事型だけか
5. 自動テストできる部分があるか

個別事象のたびに新ファイル・新チェックを増やさない。

## 9. 削除・統合原則

- 品質基準そのものは、単に「長い」という理由で削除しない。
- 重複は正本へ統合し、参照側を短くする。
- 過去レビューとの互換性が必要なID・ファイルパスは段階的に廃止する。
- 固定記事数、固定年号、固定ページ数など、運用拡大で陳腐化する条件は避ける。
