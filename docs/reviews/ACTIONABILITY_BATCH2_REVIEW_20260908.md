## B018 地震で車が壊れた場合、自動車保険はどう考える？

### 判定

`NEEDS_REVISION`

### 良い点

- 地震・噴火・津波と、台風・洪水・高潮を原因別に分けている。
- 住宅の地震保険と自動車保険を混同していない。
- 津波浸水地域へ車を取りに戻らない、浸水車を始動しない、高電圧系統へ触れない等、安全境界は明確。
- 写真だけでなく、時刻・場所・駐車/走行状態を時系列で残す説明がある。
- ローン・リース、代車、レッカー、買替時の特約引継ぎまで論点は広くカバーしている。

### 不足

1. **契約確認の初回操作が分散している。**
   - 「地震等特約を確認」「支払条件を見る」は複数回出るが、保険証券・契約者ページを開いた読者が最初に見る項目が一か所にまとまっていない。
2. **類似H2が多く、優先順位が見えにくい。**
   - `地震等特約は通常の車両保険と同じとは限らない`
   - `車両保険に入っていても地震補償は自動ではない`
   - `特約は名称ではなく支払条件を見る`
   は一つの「契約で確認する項目」章へ統合できる。
3. **平常時と被害後の行動が交互に出る。**
   - 読者の時間軸として、`平常時の契約確認 → 被害直後の安全 → 記録 → 連絡・修理`へ再配置した方が理解しやすい。
4. **特約加入判断の例が抽象的。**
   - 沿岸部の月極駐車場、ローン残高が大きい、通勤で代替交通が少ない等を1ケースにまとめると自分ごと化しやすい。

### 修正方針

- 冒頭に「証券・アプリを開いたら4点」の確認ボックスを置く。
  1. 車両保険の有無
  2. 地震・噴火・津波を対象とする特約の有無
  3. 特約の支払条件・支払額/限度額
  4. ロードサービス・代車・連絡先
- 特約関連の重複H2を統合。
- 本文の大分類を `平常時 / 被害直後 / 手続き / 加入判断` に寄せる。
- 数値や補償内容は商品横断で一般化せず、現在の契約・約款確認を維持する。

## B016 台風の風災は火災保険でどう扱われる？

### 判定

`NEEDS_REVISION`

### 良い点

- 台風という災害名ではなく、風災・水災を原因で分けている。
- 経年劣化を火災保険の修繕制度と誤解させない。
- 屋根へ上がらない、安全な範囲の撮影、悪質な修理勧誘への注意がある。
- 家財、カーポート・物置、応急処置、賠償責任など実際に迷いやすい論点を扱っている。

### 不足

1. **被害後に何から始めるかが散らばっている。**
   - 写真、保険連絡、修理見積り、応急処置、修理契約の説明が複数のH2へ分散。
2. **証券の確認方法をもう1段具体化できる。**
   - `風災・雹災・雪災`、建物/家財、免責だけでなく、「被害物→原因→契約対象→補償→条件」というB019と共通の見方へつなげるとサイト全体で一貫する。
3. **雨漏りの具体例を1ケースにまとめる余地がある。**
   - `強風で屋根材が破損→そこから雨水侵入` と `以前から劣化→台風の日に雨漏り発見` を並べると、原因確認の意味が直感的になる。
4. **後半の短い章が並び、重要度が均等に見える。**
   - `飛来物 / 付属設備 / 応急処置 / 見積り / 連絡順 / 近隣被害` は「被害別・手続き別の追加確認」としてまとめられる。

### 修正方針

- 冒頭に `安全 → 被害全景 → 原因メモ → 契約確認 → 保険会社連絡 → 修理契約` の行動順を置く。
- B019の5段階フレームへ内部リンクし、保険記事間の確認方法を統一する。
- 「屋根破損後の雨漏り」と「経年劣化での雨漏り」を対比ケースで説明。
- 修理関連H2を統合し、悪質業者注意を主フロー内に置く。

## B004 停電に備えて準備しておきたいもの

### 判定

`MINOR_REVISION`

### 良い点

- 大容量電源の購入から始めない方針が明確。
- 照明、情報、連絡、充電、生活維持まで網羅。
- 冷蔵庫、夏、冬、医療機器、復電火災、断水等への内部リンクがある。
- ポータブル電源を必須とせず、用途と負荷から考える構成になっている。

### 不足

冒頭では「暗闇・情報・連絡」の3点を最優先とし、その直後に5分類を提示するため、読者には「3つなのか5つなのか」が一瞬分かりにくい。

### 修正方針

次の関係を明記する。

- **最初の3つ** = 停電直後に失うと困る「初動優先」
  - 照明
  - 情報
  - 連絡
- **残り2つを加えた5つ** = 数時間〜数日を含めて家庭全体を点検する「棚卸し分類」
  - 充電
  - 生活維持

さらに、5分類ごとに「家にある / 動作確認済み / 足りない」の3列で確認すると、商品購入ありきにならず不足だけを把握できる、と具体化する。

## B020 大雨の前に自宅で確認すること

### 判定

`PASS_NO_CHANGE`

- 3〜7日前、2〜3日前、前日、当日の時間軸が明確。
- 屋外作業を止める中止条件が具体的。
- 線状降水帯の半日前・直前・発生情報を、単独の避難スイッチにしていない。
- 家族不在、乳幼児・高齢者・ペット、賃貸、上階移動など生活条件が具体的。
- 商品記事・避難記事への文脈内リンクがある。

トリアージで短いH2が多数出たのは、時系列チェックリスト型の記事構造によるものが大きい。長文化しない。

## B015 浸水後、片付ける前に記録したいもの

### 判定

`PASS_NO_CHANGE`

- 全景→浸水高さ→損傷部→型番の順番が具体的。
- 写真とメモの記載例がある。
- 危険なら撮影を後回しにする境界が明確。
- 処分前、緊急修理、領収書、受付番号、時系列まで後工程につながる。
- 「遠景・中景・近景」「部屋ごとの一覧」等、初心者が実行できる具体性がある。

短いH2は個別の記録テクニックであり、現状の方が参照しやすい。

## B014 浸水した家財は保険の対象になる？

### 判定

`PASS_NO_CHANGE`

- 家財契約→水災→条件→記録→連絡という確認フローがある。
- 建物と家財、賃貸、現金・高額品、仕事用機器等の条件差が説明されている。
- 写真・型番・購入資料等、被災後に残すものが具体的。
- 保険だけでなく家財の高所移動等の事前対策へつながる。

後半に個別論点の短いH2が多いが、内容は重複ではなく条件別の参照項目であるため、文字数警告だけを理由に統合・増量しない。
