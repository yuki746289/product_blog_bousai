# 防災ブログ 説明品質・生活者リアリティ プレフライト

作成日時: 2026-09-08 13:52 JST
適用対象: 防災ブログの全記事・Q&A・商品導線を含む本文修正
位置づけ: public側作業コピー
正本: `yuki746289/product_blog_rules` の `sites/bousai/rules/EXPLANATION_QUALITY_PREFLIGHT.md`

## 1. 目的

記事の質を「総文字数」「正しい情報が書いてあるか」だけで判定しない。

読者が各章を読んだときに、少なくとも次の疑問へ自然に答えられる状態を作る。

- **なぜそれをするのか**
- **具体的にどうするのか**
- **何を見て判断するのか**
- **どこで確認するのか**
- **どんな場合は別の対応になるのか**
- **自分の生活で実際にできる行動か**

事実として間違っていなくても、因果関係・前提・具体的方法が抜けていて読者が行動へ移せない説明は不十分とする。

また、機械的な定型文、抽象的な注意書きの連続、章構造の使い回し等によって「AIが大量生成した文章」に見える品質を避ける。これはAI判定ツールを回避するためではなく、**人間の編集者が読んでも自然で、具体的で、読者の疑問に沿った文章にするため**の品質基準である。

---

## 2. 必須の専門家視点

既存の編集・防災・UXレビューに加えて、全記事で次の2視点を必須とする。

### Q01 テクニカルライター / インストラクショナルデザイナー視点

目的:
- 手順・判断・理由の論理を飛ばさない
- 初めて読む人が前提知識なしでも意味を追える
- 「確認する」「固定する」「対策する」等の抽象動詞を、必要な具体度まで展開する

確認する問い:
- 行動の前に「なぜ必要か」が説明されているか
- 「どうやるか」が本文から分かるか
- 方法が条件依存なら、条件と確認先が分かるか
- 初出語を説明せずに結論だけ述べていないか
- 1文目と2文目の因果が読者にとって自然につながるか

### Q02 生活者UX / 行動リアリティ編集視点

目的:
- 一般生活者が実際に取る行動順に説明する
- 制度上可能でも、普通は行わない行動を標準行動として提示しない
- 「専門家として正しいが生活者には不自然」な文章を除く

確認する問い:
- 普通の家庭で本当にこの順番で行動するか
- 読者本人が行うことと、管理会社・自治体・専門業者等が行うことを混同していないか
- 読者に不要な例外・免責を先回りして説明し、主行動をぼかしていないか
- 実生活で選択肢が複数ある場合、最初に一般的な選択肢を示しているか
- 読後に「で、私は何をすればよいのか」が残らないか

## 3. 章ごとの説明充足度

### 3.1 文字数は「警告値」として使う

章ごとの文字数は品質そのものではない。短い章を機械的に水増ししてはならない。

ただし、説明不足を見つけるための警告値として次を使う。

| セクション | 標準的な目安 | 用途 |
|---|---:|---|
| 導入・結論 | 200〜400字程度 | 読者課題、結論、記事で分かること |
| 通常H2 | **400〜800字程度** | 理由、方法、具体例、注意点を説明する主要章 |
| 安全判断・避難・制度等の重要H2 | **600〜1,000字程度** | 判断材料、条件差、例外、確認先まで必要な章 |
| H3 | 200〜500字程度 | H2内の個別論点・ケース |

次は自動的なFAILではなく、**重点レビューのトリガー**とする。

- H2が概ね250字未満
- 主要H2が1〜2文だけで終了
- 200字未満のH2が複数連続
- 見出し数だけ多く、各章が説明メモ程度になっている

例外:
- 表・手順リスト・チェックリストだけで目的を十分に果たす章
- 短い結論ボックス
- 関連記事・公的情報一覧
- 同じH2直下のH3群で十分な説明がある場合

**文字数を満たすためだけの同義反復、一般論、不要な背景説明は禁止する。**

### 3.2 主要H2の内容要素

すべてを機械的に6項目入れる必要はないが、主要H2では原則として不足を確認する。

1. **結論** — 何をする / 何が重要か
2. **理由・因果** — なぜそうするのか
3. **具体的方法** — 何を、いつ、どうするのか
4. **具体例・ケース** — 読者が自分事に置き換えられる例
5. **条件・例外・注意** — 一律に言えない点
6. **次の行動・確認先** — 何を見れば判断できるか

短い章では、最低でも「結論＋理由」「行動＋具体的方法」等、読者の疑問に必要な組合せを持たせる。

## 4. 因果関係を省略しない

次のような文章は不十分になりやすい。

- 「窓際から家具を離します」
- 「排水口を掃除します」
- 「安全に固定します」
- 「建物条件で判断します」

読者は理由・方法を知らない可能性があるため、必要に応じて次まで書く。

### 悪い例

> ベランダの排水口を掃除します。

### 必要な説明

> 落ち葉や泥で排水口が詰まると、大雨時にベランダへ水がたまり、サッシ側への浸水につながる場合があります。そのため、雨が強くなる前の平常時に落ち葉・ごみ・泥を取り除き、水が流れる状態か確認します。

「行動」だけでなく**行動 → 防ぎたい問題**の因果を読者が理解できるようにする。

## 5. 初出語・突然の話題転換を防ぐ

読者が前の文脈で知らされていない語を、説明なしで突然使わない。

### 例: 養生テープ

不十分:

> テープだけで窓破損を防げる保証はありません。

改善方向:

> 台風対策として「窓ガラスへ養生テープを貼る方法」を見聞きすることがあります。ただし、養生テープは窓そのものを割れなくする保証ではありません。飛来物を減らす、雨戸・シャッターを使う、カーテンを閉めて窓から離れる、といった対策を先に考えます。

初出語では必要に応じて、
- 何のための物・制度・情報か
- なぜ今その話をするのか
- この記事ではどこまで扱うのか

を先に示す。

## 6. 抽象語を具体化する

次の語は便利だが、説明不足を隠しやすい。

- 適切に
- 安全に
- 必要に応じて
- 十分に
- 固定する
- 対策する
- 確認する
- 建物条件
- 状況に応じて
- 自治体情報

これらを使った場合、読者が「具体的には？」とならないか確認する。

### 「固定する」の例

- 最優先: 室内へ移せる物は室内へ移す
- 移せない物: 製品・設備の取扱説明や建物ルールに合う固定方法を確認する
- 高所作業や外装施工: 強風時に自分で行う行動として勧めない

記事側で安全な固定工法を一般化できない場合は、曖昧な独自工法を作らず、**どこまで本人が行い、どこから専門家・管理者へ確認するか**を明確にする。

### 「自治体の避難情報と建物条件」の例

単に「確認する」で終えず、テーマに応じて具体化する。

- 市区町村の警戒レベル・避難指示等
- 洪水 / 高潮 / 土砂災害等のハザードマップ
- 想定浸水深
- 家屋倒壊等氾濫想定区域
- 土砂災害警戒区域
- 自宅階と建物階数
- マンションの防災計画・管理規約
- 停電・断水・エレベーター停止時の生活継続性

さらに「どの情報をどう判断に使うか」を本文で説明する。

## 7. 生活者として不自然な行動を標準化しない

一般の住民が通常は行わない行動を、禁止事項を書くためだけに本文へ持ち込まない。

### 例: マンション共用部の土のう

不自然:

> 個人で共用部へ土のう・止水板を置く前に、管理規約を確認します。

改善方向:

> エントランスや共用廊下など共用部の止水対策は、通常、管理会社・管理組合側の運用を確認します。1階住戸では、自宅玄関付近の浸水リスクと、建物側で決められている止水・避難方法を事前に確認します。

「あり得るが普通ではない行動」を防ぐ注意書きより、**一般的な読者がまず行う行動**を先に書く。

## 8. AI定型感・機械的文章のレビュー

次の傾向が複数ある場合は編集し直す。

- 章ごとに毎回同じ「結論→箇条書き→注意→まとめ」型を使う
- 「重要です」「確認します」「考えます」「必要があります」が機械的に反復する
- 一般論と免責だけで章が終わり、具体例がない
- 箇条書きを文章へ戻しても新しい情報がほとんどない
- 別記事の地名・災害名だけ差し替えたように見える
- 読者が当然知りたい「なぜ」を飛ばし、ルールだけ列挙する
- 「〜の場合があります」を重ねすぎて結論が見えない
- 専門用語を正確に並べる一方、生活場面への翻訳がない
- 制作メモのような「候補」「確認ポイント」「記事内容に沿って」等の語が本文へ出る

改善では、口語化や感情表現を増やすことを目的にしない。**具体的な生活場面、因果関係、判断材料、自然な話題接続を増やす。**

実体験・専門資格・被災経験を創作して「人間らしく」見せることは禁止する。

## 9. 商品語からの商品記事導線

具体的な商品カテゴリ・用品名が本文で自然に出る場合、読者が「どれを選べばよいか」と次に考える可能性がある。

例:
- 養生テープ
- 飛散防止フィルム
- 携帯トイレ
- 防じんマスク
- ゴーグル
- 懐中電灯
- モバイルバッテリー
- ポータブル電源

### 基本導線

```text
情報記事
  ↓
用途・選び方を説明する商品記事
  ↓
Amazon
```

ルール:

1. 商品語が出たという理由だけでAmazonへ直接リンクしない。
2. **既に対応する商品記事がある場合**、必要性・用途・限界を説明した直後に自然な内部リンクを検討する。
3. アンカーは「養生テープはこちら」のような曖昧表現ではなく、遷移先の役割が分かる文言にする。
4. 同じ商品記事へのリンクを章ごとに繰り返さない。
5. 安全行動を説明する前に購入CTAを置かない。
6. 対応商品記事が存在しない場合、Amazonへ直結させるためだけに薄い商品記事を作らない。検索意図・購入判断量・既存記事との役割差を確認して新規商品記事候補とする。
7. 商品記事・Amazonを扱う作業に進む場合は `AMAZON_WORK_PREFLIGHT.md` を必ず実行する。

### 養生テープの扱い

`養生テープ` が台風・窓対策記事に出る場合は、まず本文で「何のために使われるのか」「窓を割れなくする保証ではない」ことを説明する。

対応する窓対策商品記事が存在する場合は、その説明直後から商品記事へ誘導できる。存在しない場合は、B046等の情報記事からAmazonへ直接つなぐのではなく、**「台風の窓対策用品」等の商品記事を作る価値があるかを別途判定する。**

## 10. 公開前チェック

記事の新規作成・大幅修正では、主要H2ごとに最低限次を確認する。

- [ ] 章の結論が分かる
- [ ] 「なぜ」が必要な行動には理由がある
- [ ] 「どうする」が必要な行動には具体的方法がある
- [ ] 初出語を突然使っていない
- [ ] 「確認する」場合、何を・どこで確認するか分かる
- [ ] 抽象語だけで行動を済ませていない
- [ ] 普通の生活者が実際に取る行動順になっている
- [ ] 管理会社・自治体・専門業者と個人の役割を混同していない
- [ ] 条件・例外が必要な場合は具体的に示した
- [ ] 章が短い場合、情報不足ではなく本当に短く完結する内容か確認した
- [ ] 機械的な定型文・同義反復・免責の連続になっていない
- [ ] 商品語が出た場合、対応商品記事への自然な導線を検討した
- [ ] 商品導線がある場合、Amazonプレフライト適用要否を確認した

判定は `PASS / FAIL / N/A` とし、主要な修正記事では記事別チェックリストへ `explanation_quality_review: PASS` を記録する。

## 11. 既存記事の再レビュー

既存記事は一括で文字数を増やさない。

次の順に問題箇所を抽出する。

1. 短いH2 / 1〜2文だけの主要章
2. 「安全に」「適切に」「確認する」「固定する」等で終わる章
3. 初出語が突然現れる章
4. 理由のない行動指示
5. 読者本人が通常しない行動を前提にした説明
6. 「自治体情報」「建物条件」等が具体化されていない説明
7. 商品語があるのに、既存商品記事への自然な導線を見落としている箇所
8. 他記事と構造・言い回しが過度に似る箇所

修正は問題がある章だけを対象にし、内容が既に十分な章を文字数基準だけで膨らませない。
