## 1. 目的

全記事を「事実が正しい」「総文字数が足りる」「必要な項目が存在する」だけで公開可としない。

最終レビューでは、読者が**記事全体を一つのストーリーとして理解できること**を最優先する。読者が記事を読んだ結果として、

- タイトルから期待した答えが、自然な順序で得られる
- 冒頭で「この記事は何を、どの順番で説明するか」が分かる
- 各章が前後の章とつながり、「なぜ今この説明なのか」が分かる
- 自分に関係する条件が分かる
- なぜ必要か理解できる
- 初めてでも確認・操作・行動まで進める
- 現実の生活で取り得る行動になっている
- 必要な関連記事・商品記事へ自然に進める
- 図や画像が必要な箇所では視覚的に理解できる
- 制作側のメモや未完成表現が一切見えない

状態を目標とする。

判定は `PASS / FIX / HOLD / N/A`。公開NG項目、ストーリー破綻、タイトルと本文の大きな不一致が1つでもあれば `PASS` にしない。

## 2. P0 公開本文の衛生チェック（最優先）

### 2.1 内部メモ・制作コメントを本文へ出さない

次のような制作側の都合・未完成表現は**公開本文では厳禁**。

- 「別途検討します」
- 「今後追加します」
- 「商品記事を作成予定です」
- 「この記事からAmazonへ直接つなげず…」
- 「商品候補」「採用理由」「記事内容に沿って選定」
- 「編集メモ」「作業メモ」「TODO」「FIXME」
- 「この箇所は後で修正」等の制作工程の説明

必要な内容が未作成なら、本文に制作事情を書かない。読者に現在提供できる情報だけで文章を完結させる。

### 2.2 読者向け文章への変換

内部判断が必要な場合は、公開本文では読者価値へ変換する。

不適切:
> 止水板の商品記事は別途検討します。

適切な方向:
> 止水板は開口幅、設置高さ、固定方法が製品ごとに異なるため、購入前に自宅の設置場所を測り、製品の適合条件を確認します。

### 2.3 公開前の強制確認

- [ ] Markdown本文に内部メモがない
- [ ] preview / production HTMLに内部メモがない
- [ ] 「予定」「検討」「候補」等が読者向け意味ではなく制作都合として残っていない
- [ ] 仮リンク、`href="#"`、準備中UIが残っていない
- [ ] 文章途中・仮見出し・重複章がない

**P0にFAILがあれば即修正。その他の品質判定へ進まない。**

## 4. 記事全体のストーリー設計（最重要）

### 4.1 冒頭に「記事の地図」があるか

導入では、少なくとも次の3点が初見で分かる状態を基本とする。

1. **何が問題か** — 読者が今なぜこの記事を読むのか
2. **先に知るべき結論** — まず何をすればよいか / 何を理解すればよいか
3. **この記事で何を説明するか** — 以降の章の意味・順番

「結論を先に書く」ことと、「結論だけを突然置く」ことは別。結論の後に続く説明が**何のための説明か分かる一文**を入れる。

### 4.2 章順が読者の疑問順になっているか

原則として、テーマに応じて次のような自然な順を選ぶ。

- 入門記事: `概要 → 何をするか → なぜ → 方法 → 条件別 → 次の行動`
- 使い方記事: `対象物とは何か → 使い方 → 注意点 → 必要数/選び方 → 保管/処分`
- 保険記事: `対象になるか → 条件 → 自分の契約確認 → 被災後の行動`
- 災害前記事: `いまの判断 → 時間軸 → 具体的行動 → 中止条件`
- 災害後記事: `安全確保 → 記録 → 連絡/手続 → 清掃/修理等`
- 商品記事: `用途・誰向け → 選び方 → 商品比較 → 注意点 → 購入導線`

上記は固定テンプレートではない。**検索意図に最も自然な順を選ぶ。**

### 4.3 見出し同士がつながっているか

- [ ] H2/H3が独立したメモの寄せ集めになっていない
- [ ] 前章を読んだ後に「なぜ次がこの章なのか」が理解できる
- [ ] 分類を提示した直後に、分類を使って本文を展開している
- [ ] 冒頭で示した手順・分類と、後半の見出し構造が食い違っていない
- [ ] 同じ論点が離れた複数章に分散していない
- [ ] 後半に重要情報を足した結果、同じテーマが重複していない

### 4.4 結論と説明の対応

結論で3点を示したなら、本文で3点がどこで説明されるか追えること。5分類を示すなら、その5分類が読者の理解にどう役立つかを説明する。

例: 「最初の3点」と「5つの役割」が併存する場合は、**3点は優先順位、5つは準備漏れ防止の分類**など、関係を明示する。

### 4.5 読後の着地点

- [ ] 最後に「結局、自分は何をするか」が残る
- [ ] 今日できる行動、確認先、関連記事等へ自然に接続する
- [ ] 本文中ですでに必要になったリンクを、最後だけに押し込んでいない

## 5. 章ごとの説明充足

章の文字数は**ノルマではなく警告値**として使う。

| セクション | 警告目安 |
|---|---:|
| 導入・結論 | 200〜400字程度 |
| 通常H2 | 400〜800字程度 |
| 安全・避難・制度判断の重要H2 | 600〜1,000字程度 |
| H3 | 200〜500字程度 |

短くても目的を完結できればPASS。長くても説明が曖昧ならFIX。

主要章では必要に応じて次を確認する。

1. 結論 — 何をするか
2. 理由 — なぜするか
3. 方法 — 具体的にどうするか
4. 具体例 — 生活場面へ置き換えられるか
5. 条件・例外 — 一律でない点
6. 次の行動 — 何を見る、どこで確認するか

- [ ] 「確認する」「固定する」「安全に」「適切に」で説明を終えていない
- [ ] 行動と理由の因果がつながっている
- [ ] 初出語を突然出していない
- [ ] 独自の分類・段階・優先順位を使う場合、なぜその分け方が役立つか説明している

## 6. 箇条書き・表の説明品質

箇条書きは情報圧縮の手段であり、**説明を省略する手段ではない**。

- [ ] 読者が用途を知らない備品・制度・行動を名詞だけで並べていない
- [ ] 「何に使う」「なぜ必要」「いつ使う」「注意点」のうち必要なものが分かる
- [ ] 3項目以上の備品列挙で用途差が重要なら、表への変換を検討する
- [ ] 表の各列には比較する意味がある
- [ ] 箇条書き前後に、その一覧をどう使うか説明がある

例:

| 備品 | 何に使う | なぜ必要か |
|---|---|---|
| ヘッドライト | 暗所での移動・作業 | 両手を空けやすい |
| 携帯ラジオ | 災害情報の取得 | スマホ通信・充電が使えない場合の代替になる |

## 7. 初心者が操作完了できるか

「見てください」「確認してください」だけでは不足。

必要な記事では、

- どのサイト・ページを開くか
- どのメニュー・災害種別を見るか
- 住所等をどう入力するか
- 地図・凡例・数値の何を見るか
- 見た結果をどう次の判断へ使うか

まで説明する。

例: ハザードマップなら「ポータルを開く→住所検索→災害種別→凡例・想定浸水深→自治体版確認」までを一つの作業として扱う。

## 8. 生活者リアリティ・継続性

- [ ] 一般家庭が通常行わない行動を標準行動にしていない
- [ ] 個人・管理会社・管理組合・自治体・専門業者の役割を混同していない
- [ ] 「半年に1回確認」等、記憶だけに依存する運用を安易に勧めていない
- [ ] 定期作業にはカレンダー、更新日、季節行事、引っ越し・進学・保険更新等の**忘れないトリガー**を提案している
- [ ] 危険時の「やること」だけでなく「中止条件」が必要な記事では明示している
- [ ] 普通の読者が迷う場面をケースとして1つ以上具体化している

## 9. 数量・設置・比較を具体化

数量や物理設置が重要な記事では、可能な範囲で具体的にする。

- [ ] 「多めに」「十分に」だけで終わらず、算定方法や基準元を示す
- [ ] 全国一律にできない数量は、計算式・測り方・例を示す
- [ ] 設置物は「どこに」「どう置く」「何を測る」「いつ中止する」を説明する
- [ ] 実験値・自治体例・メーカー値を全国共通の安全保証に読み替えない

## 10. 画像・図解の挿入判断

### 10.1 画像を入れる価値が高い箇所

次のいずれかに当てはまる場合、文章だけで済ませず図・写真・模式図を検討する。

- 初見では物の形・違いを想像しにくい
- 位置関係・配置・設置方法を説明する
- 3段階以上の手順を説明する
- A/Bの違いや分類を理解させる
- 「どこを見るか」を説明する
- 水・風・避難経路等の流れを理解させる
- 家の中・ベランダ・車内など空間配置を説明する
- 文章だけだと誤解しやすい因果関係がある

例:
- 携帯トイレと簡易トイレの違い
- ハザードマップの見方
- 土のうの並べ方・継ぎ目のずらし方
- ベランダ排水口とサッシの位置関係
- 停電の役割分担
- 津波避難の高低差

### 10.2 画像の優先順位

1. **公式図・一次資料** — 安全判断、制度、警報体系、地図UIなど正確性が重要
2. **実物写真** — 商品、設備、実在場所、具体的な物の形を示す
3. **独自図解 / AI生成図** — 空間配置、手順、比較、概念説明で公式図がない場合
4. 雰囲気写真 — 読解価値がある場合のみ

### 10.3 AI画像を使ってよいケース

- 一般住宅の模式図
- 家具配置や備蓄配置の説明図
- 土のう等の原理を説明する概念図
- 避難判断フロー
- 停電準備の分類図
- 特定の実在被害を再現しない一般的な防災イラスト

### 10.4 AI画像を使わないケース

- 実在商品の商品写真代用
- 歴史災害の「当時写真」と誤認されるもの
- 現在の被災地・事故現場写真の代用
- 気象庁・自治体等の公式画面を正確に再現する用途
- 数値・安全基準を視覚的に断定する図で根拠がない場合

AI画像が現実写真と誤認され得る場合は「図解」「イメージ」等のキャプションで区別する。

### 10.5 画像品質

- [ ] 章の説明を助ける目的が明確
- [ ] 枚数合わせではない
- [ ] 日本の住宅・生活環境と矛盾しない
- [ ] 図内文字は日本語で読みやすい
- [ ] スマホで潰れない
- [ ] altは画像の役割を説明する
- [ ] 同じ画像を複数記事へ機械的に使い回していない

## 11. 内部リンク・商品導線

- [ ] 詳細説明済みの関連記事がある場合、読者が次に必要になる**その箇所**でリンクする
- [ ] 重要リンクを記事末だけにまとめず、本文中の文脈でも提示する
- [ ] 本文説明をリンクだけで省略しない
- [ ] 商品語（養生テープ、携帯トイレ、止水板等）が自然に出る場合、対応商品記事の有無を確認する
- [ ] 商品記事が存在する場合は原則 `情報記事 → 商品記事 → Amazon`
- [ ] 商品記事が未作成の場合、**「今後作る」「別途検討」等を公開本文へ書かない**
- [ ] Amazon関連作業では `AMAZON_WORK_PREFLIGHT.md` を必ず実行する

- [ ] 数値・制度・警報体系は現行情報か確認
- [ ] 公式情報とサイト独自の説明を混同していない
- [ ] 一律の安全保証を作っていない
- [ ] 危険作業を「自己責任で」等の免責だけで勧めていない
- [ ] AI生成画像・図を事実写真・公式図として見せていない
- [ ] 実体験、資格、被災経験を創作していない

## 13. AI定型感・編集品質

- [ ] 同じH2構造を複数記事で機械的に反復していない
- [ ] 「重要です」「確認します」「必要です」が連続していない
- [ ] 「場合があります」の連発で結論が消えていない
- [ ] 箇条書きが単なる名詞列ではなく、必要な理由・使い方がある
- [ ] 読者の実際の疑問順に記事が進む
- [ ] 制度説明だけでなく生活場面へ翻訳している
- [ ] 不自然な免責・注意書きを主文章より先に出していない

目的はAI判定回避ではなく、**人間編集者が最初から最後まで読んでも自然で、具体的で、一本の話として完成した記事にすること**。

## 14. 修正箇所の記録（必須）

`FIX` を付ける場合は「記事全体を修正」だけで終わらせない。レビュー台帳へ、可能な限り次を記録する。

- H2 / H3見出し名
- 該当段落の冒頭文、または問題文
- 問題の種類（ストーリー、説明不足、重複、リンク、画像等）
- どう直すか

例:

> 修正箇所: H2「明かり・情報・連絡」  
> 問題: 備品名だけが列挙され、用途と必要理由が分からない。  
> 修正: 「備品 / 何に使う / なぜ必要」の表へ変更する。

修正後は同じ箇所を再レビューし、解消したことを確認する。

### 全60記事レビュー完了条件

- B001〜B060すべてに最終判定がある
- 全記事で `story_quality` と `title_promise` を確認済み
- `FIX` は修正箇所を記録し、修正後に再レビュー済み
- `HOLD` は公開継続可否・理由が明示されている
- 公開NG文言が0件
- 画像追加が必要な記事は `visual_support: ADD` と挿入候補章を記録
- 商品導線候補は内部メモではなくレビュー記録へ保存
- 全記事の最終レビュー結果を一覧ファイルへ集約する

このチェックリストを通過するまで、全記事見直しを完了扱いにしない。
